## H. 算子缺汇编实现（铁律八的覆盖断言本身也缺）

铁律八要求每个算子七种实现（标量 C + MMX/SSE/SSE2 × intrinsics/asm），
并要求一条**覆盖断言**：两个构建各自报告的档位取并集必须恰好覆盖
「格式 × 七种」，缺的格子要带原因。**那条断言不存在**，所以下面这张表是
手工数出来的，而不是任何东西自动报出来的——这本身就是缺失的设施之一。

### H1 / H2 —— 这张表现在由机器产出（2026-08-18）

**手工维护的那两张表是错的，而且错在高估。** 它们说 q4_1 / q6_1 / q8_0
有 gcc 的 128 组内核——**一个都没有**，`ops_kernel_dot.h` 里每一个
`dot128_*` 都是 Watcom 的 `#pragma aux`。没有任何闸门看得见这件事：
`test_dispatch_equiv.py` 那条覆盖断言查的是**档位名的并集**，而
「某个格式缺某个内核」不改变档位名集合。

所以这张表不再手写。`llama98 --kernel-matrix` 由 `lz_kernel_matrix()`
从 `LZ_ROW_*` 表直接产出，两个构建取并集：

```
format mmxI sseI sse2I mmxA sseA sse2A  g128
q8_0   x    .    x     x    .    x      G
q4_1   x    .    x     x    .    x      G
q6_1   x    .    x     x    .    x      G
q16_0  x    .    x     x    .    x      G
t2     x    .    x     x    .    x      .
```

**H1 完成**：五个格式的四个非 SSE1 格全齐。此前「T2 缺」是按符号名检索
的误判——它的 SSE2 intrinsics 内联在 `row_t2_sse2_intrin` 里，没有独立符号。

**H2 的真实状态**：`g128` 那一列 Watcom 侧四个格式有、T2 没有。gcc 侧原为
「没写」，**2026-08-20（任务 #12）已补写**（`dot128_*_mmx`，
`src/ops_kernel_dot_mmx.h`，走 `LZ_G128_GCC` 旋钮默认开），现在两侧并集仍是
上表。T2 的空格理由不变，单独记：

- **T2 无可摊销，是结构性的。** 对照 q6_1——它同样解 2 位平面**却有** 128 组内核，
  因为它跨四个子块提升了两个掩码常量（0x0F 与 0x03）加一个零寄存器。T2 的解包
  只有一个零寄存器加三个立即数移位，把零提升出去只是把 `pxor mm2,mm2` 换成
  `movq mm2,mm7`，一条换一条；每个子块自带 2 位平面、自带累加器、自带折叠。
  它的 128 组内核会发出与四次 32 调用**逐条相同**的指令序列。
- **gcc 侧曾经是「没写」，不是「没东西可提供」。** 汇编版手工提升的那些循环
  不变量，编译器本来就会提升；但「手写版会不会与编译器产物不同」当时没量过，
  所以不许写成结构性空缺。现已补写：`z`/`m0f`/`m03` 跨四个子块存活，
  与 Watcom 汇编同形，`chk=` 逐位一致；**收益仍未量**（铁律三：目标机实测）。
  旋钮 `LZ_G128_GCC` 置 0 可退回逐 32 路径做对照。

**闸门 `tests/test_kernel_matrix.py`**（训练树）：空格必须在登记表里带理由，
**而且反向也查**——已经填上的格子如果还留着「为什么空」的理由，同样红。
变异矩阵 `.prof/mut_kernel_matrix.py` 三个变异各只红自己那条：删掉
t2 的 sse2-intrin（此前所有闸门都看不见）、给 t2 填上 g128 而不撤理由、
从矩阵里删掉一个格式。

### H3. 五个算子的格子

| 算子 | 七格里有几格 | 备注 |
|---|---|---|
| `lz_quantize_q8` amax 扫描 | **5/7**（2026-08-18） | 标量 C + MMX/SSE2 各两侧；**SSE1 那格结构性为空**，理由已写下 |
| `lz_rmsnorm` 输出循环 | **3/7**（2026-08-18） | 标量 C + SSE/SSE2 两侧共用一份（`mulps`/`addps` 是 SSE1，SSE2 加的东西这里用不上）；**MMX 那格结构性为空**——MMX 是纯整数指令集。平方和那半仍是标量 |
| `lz_causal_conv1d_step` | 0 | **不是不可能，是没写**——见下方「跨通道」一段 |
| `lz_rmsnorm_gated` | 0 | 输出循环逐元素调 `lz_silu`，跟着 silu 走 |
| `lz_softmax` max 扫描 + 归一化 | **3/7**（2026-08-18） | 两处都是 SSE1（`maxps` / `mulps`），MMX 那格结构性为空。**求和那半仍是标量** |
| `lz_silu` / `lz_sigmoid` | 0 | **结构性**：两条路都要查表——定点档是 Q15 表，浮点档的 `lz_exp` 是 32 项 `2^(k/32)` 表——而 MMX/SSE2 都没有 gather，四条 lane 的索引各不相同就没法一次取 |

**这里有一条把剩下四个卡住的结构性事实，值得单独写下**：铁律二要求七格之间
逐位一致，而**浮点求和的向量化必然改结合顺序**，所以 conv 的 MAC、RMSNorm 的
平方和、softmax 的求和都不能直接向量化——要做只能另开一个自身逐位一致的独立档
（形如本会话那四个定点旋钮）。

**能直接向量化的是「逐元素」与「精确归约」两类。** amax 属于后者：max 精确且
可结合，lane 顺序改不了答案，所以它是这五个里唯一能立刻拿到逐位一致 SIMD 的。
掩掉符号位后所有值非负，于是 MMX/SSE2 只有的**有符号** 32 位比较也正确。

**conv1d 有第三条路：跨通道，不跨抽头。** 卷积是 **depthwise** 的——通道 c 的历史
只和通道 c 的抽头相乘——所以四个**通道**并行时，每个通道的 k 项求和**顺序不变**，
逐位一致成立。挡路的是布局而非算术：权重是 `w[c*k + j]` 通道优先，k=4 时四个通道
的权重是连续的 16 个 float，一次 4×4 转置（`_MM_TRANSPOSE4_PS`，SSE1）就变成抽头优先；
历史是 `state[c*hist + j]`，hist=3 不是 4 的整数倍，那一半要另想。**没写。**

按同一判据，剩下明确可做的只有这一项。silu/sigmoid 那两格是真的没有指令可用。

### H4. ARM 的表 —— 已补（2026-08-18）

铁律八现在有第二张表：ARMv5TE 是**标量 C + 手写汇编**两格，不是七格表的一格
——没有 SIMD 意味着坐标系不同，不是缺格。汇编格列了能用的指令
（`SMLAxy` / `SMLAL` / `QADD` / `LDRD` / `PLD`），覆盖断言相应也是两份。

**2026-08-21：汇编格不再是空的，而且这一节不该再手工维护状态。**
手写 ARMv5TE 内核已落地（三值、Q8_0、Q16_0 各自的 C 与汇编格），
`--kernel ref/arm-c/arm-asm` 三档在 T2 检查点上逐位一致，并配了外科变异
（改掉汇编里一个立即数 → 95.6% 字节不同、`build/arm/parity_gate.sh` 退出 1）。
见 `docs/arm-ternary-tier-audit.md`。

**权威状态在 `llama98 --kernel-matrix`，不在这里。** 那张表由
`lz_kernel_matrix()` 从 `LZ_ROW_*` 机器产出，并由 kernel-matrix 闸门双向盯着
（空格要有理由，填上的格子不许留着理由）。手工复述它只会再次过期——这一节
2026-08-18 写下「汇编格是空的」，三天后就不成立了。要读 ARM 覆盖，跑那条命令。

一个仍然成立的定性结论：ARM 行内核只覆盖它自己那些格，其余格式由
`lz_matmul_xq_nt` 送去标量参考——所以在**没有 T2 张量的模型上比较三个 ARM
档位，三个都跑同一段标量代码、平凡地逐位相同**，那是假绿不是覆盖。

## 写档位梯度与丈量它的 census

六个写档位把 token 时刻的运算从 f32 挪进定点：`--recur-write`、
`--conv-write`、`--attn-write`、`--epi-write`、`--sig-write`、
`--norm-write`，外加 `--fixed auto|off|all` 作为六个档位的组开关。
census 是 `-DLZ_F32COUNT=1` 构建，在命名的位点上按 token 计数 f32
运算。下面每个数字都来自这个构建，跑在 `/tmp/kmr20`（导出的量化出货
bin，hidden 512）上。

**梯度，六档全浮点对六档全定点：**

| ctx | 浮点 | 定点 | 倍数 |
|---|---|---|---|
| 256 | 6,930,959 | 938,669 | 7.38x |
| 1024 | 12,589,583 | 1,241,758 | 10.14x |

**ctx 1024、六档全定点时的残留构成**——这是还没挪走的部分，不是挪走了的部分：

| 位点 | 计数 | 占比 |
|---|---|---|
| sigmoid | 300128 | 24.2% |
| exp | 187725 | 15.1% |
| attention scoring | 174312 | 14.0% |
| norms | 143444 | 11.6% |
| dequant epilogue | 136000 | 11.0% |
| recurrence write | 110592 | 8.9% |
| attention wsum | 106720 | 8.6% |
| conv1d | 55296 | 4.5% |
| softmax | 24616 | 2.0% |
| rsqrt | 2925 | 0.2% |
| **合计** | **1241758** | |

sigmoid 是残留里最大的单一位点，占 24.2%。sigmoid 与 exp 合计
24.2% + 15.1% = 39.3%，是残留里最大的一块，**而它已经在
`--sig-write` 后面了**——上表就是开着这个档位量的。这个档位做的是把
工作在两个位点之间搬：

| | exp | sigmoid | 合计 |
|---|---|---|---|
| `--sig-write float` | 856232 | 197280 | 1053512 |
| `--sig-write fixed` | 187725 | 300128 | 487853 |

净省 565,659，是目前量到的最大单个杠杆（总量 1,807,417 → 1,241,758）。
所以 39.3% 这一块**不是「还没人碰」，是「碰过之后剩下的」**，再降它
需要换机制，不是加一个档位。

**recurrence write 现在有位点可以量了。** 单独看这一个位点：
2,777,088 次 f32 运算（浮点）对 110,592（定点），25.1x。它在定点侧与
档位无关——`--kernel ref` 与 `--kernel mmx` 都报 110592——在浮点侧与
档位相关——ref 报 2,383,872，mmx 报 2,777,088，比值 1.164948，对上
两个内核所依据的代数值 7.0625/6.0625。

**读到 10.14x 对 8.68x 这两个数，读的是 census，不是引擎。** 两者是
同一个 ctx 1024 的模型；差别只在于 census 有没有给 recurrence write
开位点：

```
census 在 recurrence write 处没有位点     9,812,495 / 1,130,516 =  8.68x
census 在 recurrence write 处有位点      12,589,583 / 1,241,758 = 10.14x

定点侧  1,130,516 -> 1,241,758   差 +111,242
   +110,592  recurrence write，一直在跑，没开位点之前看不见
   +    650  norms，唯一真正新增到定点侧的量
浮点侧  9,812,495 -> 12,589,583  差 +2,777,088
   = recurrence write 的浮点开销，没开位点之前看不见
```

两条差额都跟上面那条 recurrence write 的单独测量逐字节对上。10.14x
这个数是**仪器修复**加一点真新增（norms），**不是引擎在两条梯度之间
跑快了。**

### 五个发现

**census 计入乘、加、除与 int/float 转换，不计比较运算，而这个缺口比
两个写档位补上的量都大。** 在 QEMU 下的软浮点 ARM 上量过：4096 个
元素、1000 次重复，一次浮点 amax 扫描花 0.409，而整条被计入账的浮点
平方和臂只花 0.247——是被计入账的工作量的 1.6x，却按 0 计。这是**一
整类运算没有位点**，不是一条路径没有位点，它把每一个碰
normalization 的档位的收益都放大了。

**norms 定点档是结构性打平，不是赢。** 把 `x` 变成整数，每个元素要花
一次浮点乘和一次取整加——这恰好就是浮点臂自己那次乘加的开销，所以
**打平就是天花板，不是没达到的目标。** 软浮点 ARM 上量过：浮点臂
0.247 对定点臂 0.251，1.02x；census 每次调用记 2 个 f32 运算，每
token 325 次调用，就是上面那 +650。它的价值在别处：它让
`epilogue -> norms -> 下一次量化` 能融合——融合之后，那次转换会消失
进 epilogue 本来就有的输出里——而不是这个档位单独跑得更快。**它没有
更快。**

**这个档位的一种实现方式代价是 3.7x，而 census 看不出来，因为它数的
是运算次数，不是运算的代价。** `lz_conv_norm_pow2`——conv 档位自己的
归一化器——它的 amax 扫描用浮点比较，取整用 `(int)(t ± 0.5f)`。同一套
装置，逐分量对比：

| | 朴素版 | 树里现有的版本 | 倍数 |
|---|---|---|---|
| amax 扫描 | 0.409 | 0.011（`q8_amax`，对清符号位后的位模式做无符号比较） | 37x |
| 量化取整 | 0.572 | 0.262（`q8_round`，magic add，不用 float→int 指令） | 2.2x |

按运算次数数，朴素版看起来只是小幅的赢。**操作数不是出货许可。**

**`-DLZ_GDN_FIXED=0` 编不过。** 四个错误，都跟 norms 档位无关：
`ops.c` 引用了未声明的 `LZ_GDN_MAX_KD`，还调用了三个没声明的函数
`gdn_pass1_fixed`、`p2_group_coef`、`gdn_p2_group_fixed`。`ops.h` 把
这个配置记成回退开关。**没有任何闸门编译它。** 一个桩函数让 norms
档位自己的代码不至于给这个构建再添第五个错误；另外那四个还在。

**`lz_gdn_quantize_2p` 加了一个 `fc_site` 参数；`tests/test_ops.c` 按
旧的参数个数调用它，连续四个提交没人查出来。** `test_ops` 在
`CTESTS` 里，所以那段时间 `make test` 与 `make test-fast` 都是红的。
三次独立 review 都没抓到，因为各自只查了一块——引擎树、探针、或者
提交本身声称的范围——没有一次把两棵树的调用点扫过一遍，也没有一次
跑过完整 target。

### 还没量的部分

上面每一个数都是 f32 运算次数，不是时间，只有一个例外：ARM 那几个
比值是 QEMU 的墙钟时间，不建模周期数。在 ARM 目标上一次 f32 乘法大约
是 28 条指令，其中只有一条是算术指令（出自
`libgcc/config/arm/ieee754-sf.S`）；在 x86 目标上 x87 做同一次运算
只要个位数周期。census 需要按目标机分开配权重，而它现在所有目标机
用同一个权重。ARM 和 x86 各自该用什么权重都没量过。能把这件事定下来
的仪器，是项目自己的平台铁律里点名的 WinChip 模拟器台架，它不存在。
